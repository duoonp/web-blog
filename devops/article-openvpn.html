OpenVPN for private Kubernetes cluster

The Problem

Securing a GKE cluster means entirely disabling its public endpoint. However, once the cluster is completely private, administrators and developers lose the ability to easily access the control plane (Master nodes) or interact directly with the cluster services and pods for debugging purposes.

The Architecture

In a standard private GKE setup, the network is strictly segmented:

  • Master Nodes: Located in a Google-managed 172.x.x.x peering subnet.
  • Nodes and Services: Placed in a 172.x.x.x VPC subnet.
  • Pods: Assigned IPs from a secondary 10.x.x.x subnet.

The Fix

The most cost-effective and controllable solution is to deploy a lightweight GCP Compute Engine instance running an OpenVPN server inside the same VPC as your GKE cluster.

By configuring the OpenVPN server to push the specific routing rules to connected clients, you can seamlessly access all cluster layers from your local machine.

Required VPN Routing Configuration:

  • Push a route for the Master Node subnet (172.x.x.x/28) so kubectl commands work natively over the VPN.
  • Push a route for the Node/Service subnet (172.x.x.x/16) to allow direct access to NodePorts and internal LoadBalancers.
  • Push a route for the Pod subnet (10.x.x.x/14) to allow direct curling of pod IPs for deep debugging.

With this setup, simply connecting your local machine to the OpenVPN client profile gives you transparent, secure access to the entire private Kubernetes perimeter as if you were sitting inside the GCP datacenter.
